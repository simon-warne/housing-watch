# M2: History and changes

## Context
PRD §6 M2 asks for three things: a SQLite schema, detection of new, changed and removed listings, and a guarantee that re-running on the same page changes nothing. PRD §5 says every observation is kept and every alert is logged. The deadline comes from `Detail` and is joined to the listing by id. M2 is offline only: the module takes a DB path, and fetching plus pushing to the `data` branch belong to M4. Once approved, this plan is saved to `docs/plans/M2.md`.

## Storage decision (needs your yes)
**I store a new observation only when a listing's state changes, not on every run.** "State" means every `Listing` field except `seen_at`, plus the deadline.

Why:
1. If nothing changed, the DB file stays byte-identical. That satisfies "re-running changes nothing", and the `data` branch only gets a commit when something actually happened (decision from 2026-11-26).
2. With a row on every run, the DB would change every 30 minutes. That means 48 commits of a binary file per day, and git history would grow by roughly 100 MB a month.

No information is lost, because each row records when that state was first seen. The answer to "how many days won" is the last observation before the listing was removed. What this does not record is that run X looked and saw no change. Heartbeat (M4) gets that from the Actions run log, not from this DB.

## Code: `src/housing_watch/history.py` (new, ~120 lines, stdlib `sqlite3`)
- **Schema** (`open_db(path) -> Connection`, which creates the tables if missing and sets `user_version = 1`):
  - `listings(id TEXT PK, first_seen TEXT, removed_at TEXT NULL)`
  - `observations(id INTEGER PK, listing_id, seen_at, area, area_code, address, type, size_m2, rent, floor, flags_json, move_in, published, top_days NULL, applicants, detail_url, deadline NULL)`, indexed on `(listing_id, id)`.
  - `alerts(id INTEGER PK, listing_id NULL, kind, state_key, sent_at, message, UNIQUE(listing_id, kind, state_key))`. M2 only creates this table. M3 fills it and uses it for dedupe.
  - All times are ISO 8601 with a UTC offset. Dates are ISO strings. Flags are stored as a JSON array.
- **`record(conn, listings, details: dict[str, Detail], seen_at) -> Changes`**, in one transaction:
  - **new**: an id that is not active in the DB, including one that comes back after being removed. It gets a listing row (`removed_at` cleared) and an observation.
  - **changed**: the state differs from the listing's latest observation. It gets an observation, and `Changes` carries `(old, new)` for M3.
  - **unchanged**: nothing is written.
  - **removed**: active in the DB but missing from this run. `removed_at = seen_at`.
  - **Deadline join**: `details[id].deadline` when this run fetched the detail page. Otherwise the last known deadline carries forward, so not fetching it this run doesn't count as a change. The list's `top_days`/`applicants` stay the source for those two fields.
  - **Empty-list guard**: if `listings` is empty, nothing is marked removed and `record` returns an empty `Changes`. PRD §4 treats 0 parsed listings as a failure (heartbeat), and a glitch must not "remove" everything and then re-alert everything as new on the next run.
- `Changes` (frozen dataclass): `new: list[Listing]`, `changed: list[tuple[Listing, Listing]]`, `removed: list[str]`, `unchanged: int`.
- `latest(conn, id) -> Listing | None` rebuilds the latest state, so M3 can compare against it. I'll add a `deadline` lookup only if M3 needs it.

## Tests first (`tests/test_history.py`; see them fail, then implement)
All tests use `tmp_path` DBs, the list and detail fixtures, and `dataclasses.replace` for variants.
1. First run on the list fixture: 24 new, 24 listing rows, 24 observations.
2. **Same page again** (new `seen_at`): 0 new/changed/removed, 24 unchanged, row counts the same, and the DB file bytes identical before and after.
3. Changed `top_days` (one listing) → 1 changed with the correct old and new values, 25 observations. The same holds for a rent change and a flags change.
4. A listing missing from the next run → removed, with `removed_at` set. Running again → it isn't removed a second time.
5. A removed listing reappears → new, with `removed_at` cleared.
6. Deadline: the first run with `Detail` stores the deadline. The next run without it → unchanged, and the deadline is kept. A different deadline → changed.
7. An empty list after a full run → nothing removed, and the DB is unchanged.
8. Round trip: `latest()` returns a `Listing` equal to the input (except `seen_at`), including tz-aware datetimes, the float size and the flags tuple.
9. `open_db` on an existing DB doesn't wipe it. The `alerts` table exists with its unique constraint.
