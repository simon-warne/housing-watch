## Rules (`rules.py`, pure functions; ~150 lines)
- **Status** for each listing: `winnable` (mine > top, or nobody has booked), `tied` (mine = top), `behind`.
- **Alert-eligible**: the type is on the alert list, the move-in date is inside the window, and either rent ≤ 6,000, or rent ≤ 7,000 *and* a stretch area *and* winnable/tied (labelled "over budget").
- **My reading of the PRD:** every run evaluates **every active listing**, not only the new or changed ones. Your days grow daily, so a listing can become winnable without changing, and dedupe stops repeats.
- **Order**: area tier, then ground floor last, then lower rent first.
- **Alerts and their dedupe keys** (`(listing, kind, state_key)`, `published` so that a re-listing alerts again):
  1. **Winnable now** (high): eligible, not booked, winnable or tied. Key `winnable|tied@published`. Going from tied to winnable alerts again; going the other way also alerts ("now tied").
  2. **Last call** (urgent): eligible, not booked, winnable or tied, and the known deadline is 0–5.5 h away. The extra 0.5 h covers a late GitHub run. Key `deadline`. Not sent without a known deadline.
  3. **Lead lost** (high): an id in BOOKED_IDS with top > mine. Key `lost@published`. Booked listings get no winnable or last-call alerts.
  4. **Weekly digest** (low): the first run after Sunday 18:00, key = ISO week. It lists the listings of alert, digest-only or unknown type seen in the last 7 days, with their status, plus a **winning-days range per area**. The range is the min–max of the last `top_days` of listings removed that week. It comes from the history DB through a new read-only query in `history.py`.
  5. **Heartbeat** (high): `state.db` keeps a failure streak (the count of consecutive failed or 0-listing runs, plus when the streak started). It is written only when it changes. The alert fires at 3 failures. Key = streak start. The M4 runner calls `run_failed()`/`run_ok()`.

## Alerts (`alerts.py`)
- `Alert(kind, listing_id, state_key, priority, title, body, url)`.
- `dispatch(state_conn, alerts, send)`: alerts whose key isn't stored yet are sent first, then stored. If a send fails, nothing is stored and the next run retries, because a duplicate is better than a miss. The stored message stays in the encrypted `state.db`.
- `history.py`: the unused `alerts` table is removed from the schema (no real DB exists yet, so v1 stays v1). `state.db` gets `alerts` (same COALESCE dedupe index) and `meta`.
