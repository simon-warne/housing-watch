## Part B plan (approved by Simon, 2026-11-26)
### Context
Part A found that BF serves every listing in one logged-out JSON (`/AllaAnnonser/`, 527 items). The detail page (`/bostad/<id>/`, HTML) adds the move-in date and the queue start dates of the top 3 applicants. You chose all five types plus Bostad snabbt, the `BF_QUEUE_SINCE` secret, the same rent limits and move-in window as SSSB, and Stockholm city, Solna and Sundbyberg only (tier 1 is the inner city). Answer from this session: a listing with no top-3 block gets **only a last call**, marked "no applicants shown" (this gets logged in DECISIONS as soon as plan mode ends). Today's fixture has 59 listings that would need detail requests (watched type, in scope, rent ≤ 7,000).

### Facts from the fixtures that shape the design
- The list's `AnnonseradTill` equals the detail page's "Anmälan senast", so the **deadline comes from the list**. It is a date only; I read it as closing at 23:59 Stockholm time (not verified), so the last call goes out about 18:59 that day.
- The detail page has **no listing id**. It is matched to its listing by `Lagenhetsnummer` and street address.
- Inflytt in the facts block was an ISO date on all 3 pages. Fallbacks (decided earlier): a month name → the 1st of that month, "så snart som möjligt" → the deadline date. Anything else raises an error.
- Bostad snabbt appears on ordinary `Hyresrätt` listings (`BostadSnabbt: true`). Today none of them is in scope at ≤ 7,000 kr.
- Rent, size and floor are null only on project ads with several units (`Antal` > 1 or `ProjektId` set). Anywhere else, a null raises an error.

### Steps (tests first for each: see them fail, then implement)
1. **`bf.py`**: `BfListing`, `parse_bf_list(payload, seen_at)` and `parse_bf_detail(html, listing) → BfDetail(move_in, top_dates)`. Both are strict like `sssb.py` (`ParseError`, no silent zeros). `bf_get` only fetches `https://bostad.stockholm.se/AllaAnnonser/` and `/bostad/<digits>/`, with the same `USER_AGENT`. Tests: `tests/test_bf.py` on the 4 fixtures plus edited copies (wrong id, missing facts, move-in as text, no top-3 block).
2. **History** (`history.py`): schema v2 adds the tables `bf_listings` and `bf_observations` (move-in and top dates stay null until a detail page is fetched). `open_db` migrates v1 to v2 in place and leaves the SSSB tables untouched. `bf_record` and `bf_active` have the same semantics as `record`: a row only on change, a 0-listing run writes nothing, a re-listed listing starts fresh. Test: migrating a v1 DB keeps the SSSB rows identical.
3. **Config**: a new `bf:` section in `config.yaml` with `types` (Lagenhetstyp names), `bostad_snabbt: true`, `municipalities` and `tier1` districts (from `docs/reports/M5.md`). Other in-scope districts are tier 2, and other municipalities are out. Rent, move-in window and last-call hours are shared with SSSB. The stretch band (6,001–7,000) applies in tier 1 only. 2+ rooms go to the digest only, as on SSSB (my reading). `BF_QUEUE_SINCE="YYYY-MM-DD"`. If it is unset, BF is still fetched and recorded and shows in the digest, but sends no BF alerts. A bad value is a setup error.
4. **Rules** (`rules.py`): `bf_status(top_dates, since)`. Earlier than the top applicant's date → winnable, same date → tied (tie → whoever applied first), later → behind. No block → `unknown` (last call only, see above). Bostad snabbt → `first_come`.
5. **Alerts** (`alerts.py`): ids `bf:<id>`; titles start "BF ·"; kinds `winnable`, `last_call` and a new `first_come`, all with the existing dedupe. The body shows district, address, rent, move-in, "top since 2020-01-17 vs yours …" and the closing date. The link is `https://bostad.stockholm.se/bostad/<id>/`. Nothing goes out after the deadline. The digest gets a BF section after SSSB's, within the same 3,900-byte limit: counts, winning dates by district for closed listings, and the listing lines.
6. **Run** (`run.py`): BF runs after SSSB in the same run, each part in its own try. A failure in one doesn't stop the other's alerts. BF has its own 25-min guard and its own heartbeat streak ("BF: N failed runs"). Detail requests are chosen by public facts only: no detail yet → fetched once; closing within 48 h → fetched every run, last-call window first; at most 10 per run, rotated, 5 s apart. The first run's 59 → about 6 runs. The log line stays fixed: `ok: N listings · bf ok: M`. Add `BF_QUEUE_SINCE` to `watch.yml`'s env.
7. **Public-trace test** extended: two different `BF_QUEUE_SINCE` values must give identical requests, history and file sizes.
8. Full check, a review by a fresh subagent (correctness and gaps against PRD and plan), the report in `docs/reports/M5.md` part B, STATUS, DECISIONS, commit, tag `m5`.
