## Förvaltaren plan (approved by Simon, 2026-11-26)

### Context
PRD §6 M6 step 1. Förvaltaren (Sundbyberg) shows "Högst köpoäng" (top points) logged out, so it gets alerts like SSSB. Your points are now in secrets `FV_POINTS` + `FV_POINTS_ON`. It is built the same way as BF in M5: its own module, tables, guard, heartbeat and digest section. A Förvaltaren failure never stops SSSB or BF.

### Facts from the fixtures that shape the design
- **List:** `GET /wp-json/fv/v1/objects?group_id=1&group_slug=lagenhet`. All 17 flats in one JSON. It has id, area, type (`objectType.name`, e.g. "1 rum o kokvrå"), rooms, rent (`cost`), floor, deadline (`showDateEnd`, a date), `usercount` (applicants) and `specialContract` (empty on all 17). It has **no move-in date and no top points**.
- **Detail:** `GET /objekt/<id>` (HTML) has Objektnummer (to match the listing), Tillträde (ISO date), Anmäl senast, Antal sökande and **Högst köpoäng** ("5 022").
- **Deadline:** given as a date only. I read it as 23:59 Stockholm, the same as BF, so the last call goes out about 18:59. The fixture was fetched at about 22:03 on its deadline day and was still listed and open. That supports end of day, but doesn't prove it.
- No page with 0 applicants or without the "Högst köpoäng" row has been seen yet.

### Design (mirrors BF; needs your yes)
- **Alerting types:** "1 rum o kokvrå", "1 rum o kök". 2+ rooms go to the digest only, and unknown types show in the digest as "other type". This is the same rule as SSSB.
- **Scope and rent:** all of Förvaltaren (Sundbyberg = tier 2), so the rent limit is **≤ 6,000 with no stretch**. Same move-in window as SSSB/BF.
- **`specialContract` not empty** (e.g. senior or youth housing): digest only, marked with its text, never an alert (not seen yet).
- **Your points:** `FV_POINTS + (today − FV_POINTS_ON)` days. Yours > top → **winnable**, equal → **tied**, top overtakes you after a winnable alert → **lead lost**. Plus a **last call** 5 h before close. Titles start "FV ·". If the secret is unset: no FV alerts, the digest still runs.
- **Detail requests** are chosen by public facts only (type, rent, `specialContract`, deadline, stored move-in), never by your points. Closing within 48 h → every run, last-call window first. Never fetched → once. Move-in known to be outside the window → never. At most 10 per run, 5 s apart.
- **Alerts only from a detail page fetched in this run.** The top figure exists only there, so an older page could be stale (the same rule as BF). No "Högst köpoäng" row → no winnable alert, only a last call marked "no applicants shown" (your M5 BF rule).
- **Strict parsing:** a layout change raises `ParseError`. A bad detail page skips only that listing; the run counts as failed for the FV heartbeat.

### Steps (tests first for each: see them fail, then implement)
1. **`fv.py`**: `FvListing`, `FvDetail(move_in, top_points, applicants)`, `parse_fv_list(json, seen_at)` and `parse_fv_detail(html, listing)`, which checks the Objektnummer. `fv_get` allows only the list URL and `/objekt/<id>`, with the same user-agent. Tests: `test_fv.py` on the fixtures plus edited copies (wrong id, missing row, non-ISO Tillträde, null rent, unknown type).
2. **Config**: a `fv:` section in `config.yaml` (types, alert types). `load_fv_points(env)` rejects a bad number or date, or a date in the future.
3. **History** schema v3: `fv_listings` + `fv_observations`. Migrating v2 → v3 in place leaves the SSSB and BF rows byte-identical (test). Rows are written only on change, a 0-listing run writes nothing, and a re-listed flat starts fresh.
4. **Rules + alerts**: `fv_status`, `fv_classify`, `fv_listing_alerts` (winnable/tied, last call, lead lost; dedupe keys as SSSB), and an FV section in the weekly digest.
5. **`run.py`**: a third `part("fv", "fv_last_fetch", "fv ", …)` with its own 25-min guard and heartbeat. The log line gets ` · fv ok: N`. Tests: an FV failure leaves SSSB and BF alerts intact. The **public-trace test** is extended: the same requests and file size for two different `FV_POINTS`.
6. **Workflow**: `FV_POINTS` and `FV_POINTS_ON` passed through env to the Watch step only, plus the workflow test.
7. `./scripts/check.sh` green. Review by a fresh subagent (correctness and PRD gaps). Report `docs/reports/M6.md` part B (Förvaltaren). Tag `m6-fv`, update STATUS. **You push.**
