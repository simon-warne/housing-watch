# M6 report, part B: Förvaltaren (2026-11-26)

## Done
- **Checks:** `./scripts/check.sh` green, 550 passed ([output](evidence/M6-fv-check.txt)). Every step was tests first, with the red run seen before the code.
- **Source:** `fv.py` reads the flat list (one JSON) and detail pages (`/objekt/<id>`). It only GETs those two URL shapes, with the same user-agent. Parsing is strict: a layout change raises an error. The detail page must carry the listing's Objektnummer and the list's deadline, and its two fact lists must agree.
- **History** schema v3: tables `fv_listings` and `fv_observations`. A v2 DB migrates in place with the SSSB and BF rows byte-identical (tested). The shrink guard covers the FV table.
- **Alerts** ("FV ·"): winnable/tied, last call (5 h before 23:59 on the deadline day), and lead lost (top overtakes you after a winnable or last-call alert). They fire only from a detail page fetched in the same run. No "Högst köpoäng" row on a flat with 0 applicants means a last call only, marked "no applicants shown". The row missing while there are applicants is a layout change, so it raises an error. A tie after your own alert on the same ad stays quiet, because it is most likely your own application.
- **Digest:** an FV section between SSSB and BF: seen, winnable, winning points per area, and one line per flat. Over-budget 1-room flats are only counted (Simon, 2026-11-26).
- **Run:** a third part with its own 25-min guard and its own heartbeat ("FV: 3 failed runs…"). The log line ends ` · fv ok: N`. An FV failure leaves SSSB, BF and the digest untouched, and the reverse holds too (tested).
- **Privacy:** detail requests are picked by public facts only. The test runs two very different point values: the alerts differ, but the requests, history rows and `state.db.enc` sizes are identical. `FV_POINTS`/`FV_POINTS_ON` reach the Watch step only. Errors never echo the values.
- **Dry run on the real fixtures** (made-up 6,000 points): Rissne is winnable on points (top 5,022) but moves in on 2027-02-01, before the window. So: no alert, and a digest line "early move-in 2027-02-01". This is as planned.

- **Review** by a fresh subagent: 3 fixes, tests first (DECISIONS.md):
  - A renamed or re-tagged "Högst köpoäng" row read as "no applicants shown". That gave an urgent last call on a flat with 40 applicants.
  - "Already alerted" ignored which ad it was, so a re-listing could give a lead lost for an ad you were never told about.
  - A 404 or timeout on one detail page dropped every alert of the run. Fixed for FV and **BF** (it had the same gap).

## Decided by Simon
The plan and its defaults (DECISIONS.md, 2026-11-26): the 23:59 deadline reading, lead-lost alerts for FV, and `specialContract` → digest only.
